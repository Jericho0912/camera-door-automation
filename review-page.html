The verdict on the god class

Asked directly, answered directly

There is no god class. The file defines exactly one class — Settings, a frozen dataclass with 18 fields and a single method.

That is the opposite of a god class: it has almost no behaviour at all. Everything else in the module is a plain function.

But the instinct is picking up something real. The god-object smell is genuinely present — it just lives in two places that aren't classes, which is why it doesn't show up when you go looking for a bloated class.

It moved into a function

process_event is 69 lines with 7 parameters and 12 branches — nearly twice the size of anything else in the file. In one scope it does six distinct jobs: completion check, segment query, state insert, per-file validation, an upload loop with interleaved state writes, manifest construction and upload, the completion write, and the Notion hand-off. Six reasons to change, one function. That is the god-class problem with the word "class" removed.

The practical cost is temporal coupling. The ordering of the state writes relative to the uploads is what makes a mid-event crash recoverable, but nothing in the code expresses or enforces that ordering — it survives only as statement order inside a long function. Defect 1 below is exactly that ordering being wrong in one place.

And into a parameter object

Settings has 18 fields, is read 44 times, and is passed to 10 of the 22 functions. Every function that receives it can reach every configuration value in the program:

  • notion_request is handed all 18 fields to read two — notion_token and notion_version.
  • upload_file is handed all 18 to read two — bucket and dry_run.

This is textbook feature envy, and it is why the S3 layer, the SQLite layer, the Notion layer and the CLI are all transitively coupled despite having nothing to do with one another. Nothing stops a future edit in the Notion code from reading settings.recordings_dir, and nothing would flag it if it did.

The fix is not "introduce classes" — it is to narrow the parameters so each function declares what it actually depends on: 

def upload_file(client, bucket: str, dry_run: bool, source: Path, key: str) -> str | None:
def notion_request(method, path, auth: NotionAuth, payload=None) -> dict:

The dependency graph then becomes visible in the signatures. Keep Settings as the single parsing point at the edge — that part is good design and the reason the test suite was possible at all.

Two supporting symptoms

The module does six jobs. One 484-line file holds configuration, schema discovery, Frigate queries, state persistence, S3 delivery, Notion sync and the CLI. The Notion feature is the evidence: one feature required edits in five places. That blast radius in a single-file program is the signal. The seam to cut first is notion — the only concern with no data dependency on any other.

There are no domain types. Events and segments are dict[str, Any] from the SQLite row all the way into the manifest and the Notion payload. Nothing validates shape at the boundary, which is the direct cause of defect 6 — a BLOB in one column crashes serialisation sixty lines from where it entered, after the uploads have already been paid for.

Twelve defects

Ordered by operational severity · each backed by a strict-xfail test

Every defect below is encoded in the suite as @pytest.mark.defect plus xfail(strict=True). Each test asserts the correct behaviour and is currently expected to fail — so fixing one turns the suite red until the marker is removed. The list cannot silently drift out of date.

01

Failures before the first state write vanish silently

High

The error handler in run_once is an UPDATE ... WHERE event_id=?, but process_event doesn't INSERT the row until line 340 — after float(event["start_time"]) and the segment query. Anything that throws before that point updates zero rows. The error is logged once and then dropped from the state database entirely, so status reports a clean system while the event is never delivered.

FixINSERT … ON CONFLICT DO UPDATE in the handler, not UPDATE.

reconciler.py:437test_cli.py::test_a_failure_before_the_first_insert_is_still_recorded
02

Losing the state DB duplicates every Notion page

High

Notion's POST /pages has no upsert, so deduplication rests entirely on the local state database. The search-before-create guard only runs if row: — that is, only when a previous attempt already left a row. With no row, it creates blind.

This isn't hypothetical. .env.example already warns that STATE_DB_PATH defaults to a relative path, so running from a different working directory creates a second empty state DB. Today that means re-uploading to S3 — wasteful but idempotent, same keys. With Notion it means a duplicate page for every event ever seen.

FixQuery Notion before creating, unconditionally — or make the state path absolute-or-fail at startup.

reconciler.py:293test_notion.py::test_losing_the_state_db_does_not_duplicate_pages
03

A BLOB in the event row crashes the manifest after the uploads

High

parse_json returns non-str values untouched, so a BLOB data column arrives as bytes, gets spread into the manifest via **event, and json.dumps raises TypeError. The segments are already uploaded and billed at that point, and the event can never reach completed_at — so it retries, and re-fails, forever.

FixCoerce or drop non-serialisable values when building the manifest; json.dumps(…, default=str) is the one-line version.

reconciler.py:374test_process_event.py::test_a_blob_data_column_does_not_break_the_manifest
04

The dry-run log leaks the person's name

High · privacy

.env.example is careful about this — it warns that sub_label is a real person's name and ships UPLOAD_EVENT_MANIFEST=false by default. But the dry-run branch of upload_manifest writes the entire manifest, sub_label included, to the log at INFO. The privacy control is bypassed by the rehearsal mode that exists to make the system safe to try out.

reconciler.py:246test_upload.py::test_dry_run_manifest_does_not_log_personal_names
05

Ctrl-C during the poll interval crashes instead of exiting cleanly

Medium
while True:
    try:
        run_once(settings)
    except KeyboardInterrupt:
        return 130
    except Exception:
        LOG.exception("Reconciliation pass failed")
    time.sleep(settings.poll_seconds)   # outside the try

The process spends nearly all of its wall-clock time in that sleep, which is precisely where a Ctrl-C lands. The handler written to give a clean 130 almost never gets the chance; the operator sees a traceback instead.

reconciler.py:480test_cli.py::test_ctrl_c_during_the_sleep_exits_cleanly
06

snapshot_db leaks a temp file on every failed poll

Medium

mkstemp runs before the backup, and only the caller's finally unlinks it. If src.backup(dst) raises — corrupt DB, locked DB, disk full — the temp file stays. Under watch that is one leaked file every POLL_SECONDS, forever.

FixWrap the backup in try/except inside snapshot_db and unlink on failure.

reconciler.py:110test_schema_discovery.py::test_failed_snapshot_leaves_no_temp_file
07

A permanently broken event retries forever

Medium

No attempt counter, no backoff, no dead-letter state. One event whose segment file was deleted will log a full traceback every POLL_SECONDS indefinitely, burying real failures in the log.

FixAn attempts column and an abandoned_at state, or exponential backoff keyed on updated_at.

reconciler.py:431test_process_event.py::test_a_permanently_failing_event_is_eventually_given_up_on
08

watch discards the failure signal

Medium

run_once returns 1 when events failed. The watch loop ignores the return value, so a launchd-managed service has no way to know anything is wrong. Only status reveals it, and nothing runs status. At minimum, log a warning when a pass reports failures.

reconciler.py:475test_cli.py::test_watch_surfaces_persistent_failures
09

No startup validation of the configuration

Medium
  • DRY_RUN=false with an empty S3_BUCKET is accepted, then fails per-event inside upload_file — a watch loop that fails 100% of events and keeps going.
  • A negative PRE_ROLL_SECONDS silently inverts the archive window rather than being rejected.

FixA __post_init__ check on Settings is the right place.

test_settings.py::test_live_mode_without_bucket_is_rejected_at_startup
10

Path traversal: uploads aren't constrained to the media root

Low · security

canonical_path returns any absolute path that exists, and relative_recording_key quietly files anything outside recordings_dir under external/<hash>-<name> rather than refusing it. A recordings.path value pointing anywhere on the filesystem is read and uploaded to S3.

The trust model keeps this low-severity — the source DB is local Frigate — but it is a full local-file-exfiltration primitive gated only on "nothing ever writes a bad path into that column", and there's no reason to accept it.

FixReject resolved paths that fall outside recordings_dir.

reconciler.py:198test_helpers.py::test_traversal_outside_the_media_root_is_refused
11

Retry-After as an HTTP-date crashes the request

Low
time.sleep(float(resp.headers.get("Retry-After") or 2 ** attempt))

RFC 9110 permits Retry-After to be an HTTP-date. float("Wed, 21 Oct 2015 07:28:00 GMT") raises ValueError, converting a routine rate limit into a hard event failure.

reconciler.py:264test_notion.py::test_http_date_retry_after_is_tolerated
12

A load-bearing invariant that only exists as statement order

Low · note

The ordering here is correct and worth stating explicitly, because it's easy to break: completed_at is written before sync_notion runs, so a Notion outage cannot make a successfully-archived event look undelivered. S3 is the product; Notion is a notification. The suite now pins this. The problem is that nothing in the code says so — the invariant lives only in statement order inside a 69-line function, which is the structural point from the verdict above.

reconciler.py:393-398test_process_event.py::test_notion_failure_does_not_undo_a_completed_delivery

Smaller items

Worth a pass, none of them urgent

  • Dead code. reconciler.py:269 — the trailing raise RuntimeError(… exhausted retries) is unreachable: range(4) makes the last attempt 3, the retry guard is attempt < 3, so a fourth 429 falls into the >= 400 branch and raises there. Coverage confirms the line is never hit.
  • Name collision. The module-level function upload_manifest and the Settings.upload_manifest field share a name. Legal, but if settings.upload_manifest: upload_manifest(…) reads badly.
  • Shadowed builtin. inspect shadows the stdlib module name — harmless today only because that module is never imported.
  • Unbounded rescan. fetch_events has no lower time bound, so every poll re-reads and re-checks the entire event history. Fine at 50 events; not at 500k.
  • Ignore hygiene. .gitignore listed only .agents and .claude, missing __pycache__, .venv, .env and the local state DB. Fixed on the branch.

What's genuinely good

The decisions that should survive any refactor

  • Settings is frozen and parsed in exactly one place. This is the single seam that made 214 tests possible without patching os.environ everywhere.
  • Schema discovery instead of hard-coded table names. resolve_table falls back to structural matching and refuses to guess when ambiguous — archiving the wrong footage is worse than failing loudly.
  • The read-only snapshot. Each pass gets one consistent view and never touches the live NVR database.
  • Segment-level delivery state. Resumption after a mid-event crash re-uploads nothing already delivered — verified end-to-end.
  • The 429-only retry policy, with the reasoning in a comment. Deliberately not retrying 5xx because a blind retry could duplicate a created page is exactly right, and the comment saying so is worth more than the code.
  • .env.example documents failure modes, not just variable names. It is the best-written file in the repo, and half the defects above were found by taking its warnings seriously.

Two notes on how it's built

The S3 client is session-scoped on purpose. Constructing a boto3 client loads botocore's service model from disk, which costs about five seconds per call when the checkout sits on a Windows drive mounted into WSL. Building it once took the suite from 140 seconds to 22. Each test still gets a freshly emptied bucket.

Time is controlled, not slept through. Segment ages are set with os.utime; the Notion backoff patches time.sleep and asserts the delays it was asked for.
